<h2>Claude API用什么IP，按协议认证与调用特征选择出口类型的方法</h2>

<p>Claude API用什么IP，选择依据和别人问网页版时不太一样。接口调用没有浏览器环境，能影响服务端判断的主要是地址、频率和请求特征，所以出口类型的权重更高。</p>

<p>先看协议支持。多数程序用 HTTP 或 HTTPS 代理就够，需要承载非网页流量时才用 SOCKS5。选错协议的表现是部分请求通、部分不通，很容易被当成地址问题。</p>

<p>再看认证方式。用户名密码适合程序自动配置，白名单适合固定机器。动态地址不适合白名单，因为地址一直在变。认证选错，配置阶段就会卡住。</p>

<p>然后是地址类型。调用对来源敏感、且需要与账号地区一致，就选住宅或 ISP；只是需要一条稳定通道，机房地址够用。不必默认选最贵的那类。</p>

<p>地区按账号记录来。注册地、支付国家、历史登录地构成合理范围，出口落在范围之内即可，不必刻意选冷门地区。</p>

<p>并发和流量口径要提前确认。并发是账号级还是地址级，超出后是排队还是拒绝；流量是单向还是双向计。这些决定高峰时会不会卡住。</p>

<p>举个假设场景：一个定时任务每小时跑一次，量不大但要求稳定。机房固定地址就够，配一条住宅反而是浪费。另一个场景是对外交付的服务，失败可见，这时住宅的稳定性才有意义。</p>

<p>技术上要防止请求绕过代理。程序依赖的第三方库、环境变量、系统代理，任一处不一致，就会有请求从本地出去。日志里出现来源跳变，先查这里。</p>

<p>还有一个细节：长连接。有些调用保持连接复用，出口变化会导致连接重建，表现为周期性超时。如果程序用了连接池，出口要尽量固定。</p>

<p>解析和 IPv6 要一起收口。请求走了代理，解析在本机完成，服务端能看到两个来源；IPv6 直连同理。</p>

<p>监控建议按出口维度聚合。同一出口的失败率突然升高，说明是线路或地址的问题；多个出口一起升高，才可能是服务端或程序的问题。</p>

<p>成本上，机房最低、ISP 居中、住宅最高。按调用量折算到每次请求，再判断这笔钱花得值不值。</p>

<p>合规是前提。不论选哪类，调用内容与频率都要符合条款与法规，出口不是豁免。</p>

<p>所以顺序是：协议、认证、地址类型、地区、并发，最后价格。前四项定完，答案基本唯一。别频繁更换，每次更换都要重配、重测、重新积累观察数据。</p>
